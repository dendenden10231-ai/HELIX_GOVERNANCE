### 2г. ПРОВЕРКА ИСХОДНОГО ФАКТА: `no-store` на ассетах НЕ ПОДТВЕРДИЛСЯ

Заданный факт звучал как «на всё выставлен `Cache-Control: no-store`, включая
assets с content-hash». **На этом объекте это не так.** Замеры выше показывают:

* `no-store` стоит ТОЛЬКО на `/` — и это сделано явно в коде, а не глобальным
  middleware. `git show 3df95f4:api/main.py`, функция `_frontend_index_or_status`:
  ```
  return FileResponse(index_path, headers={
      "Cache-Control": "no-store, no-cache, must-revalidate, max-age=0",
      "Pragma": "no-cache",
      "Expires": "0",
  })
  ```
* У ассетов заголовка кэша **нет вообще** — ни `no-store`, ни `max-age`.
* У `/api/version` и `/openapi.json` заголовка кэша тоже нет.
* Глобального middleware, который проставлял бы `no-store` на всё, в
  развёрнутом коде нет:
  ```
  $ git show 3df95f4:api/main.py | grep -inE "no-store"
  357:                        headers={"Cache-Control": "no-store",
  461:        # старый бандл. no-store заставляет всегда брать свежий index,
  465:            "Cache-Control": "no-store, no-cache, must-revalidate, max-age=0",
  ```
  Три строки, из них одна — комментарий (461), а заголовка только два:
  строка 357 — ответ двойника в `ak_deploy_guard_middleware` (503, до посетителя
  в норме не доходит), строка 465 — `FileResponse` для `index.html` (это и есть
  единственный `no-store`, который видит браузер).
* Так же и со сжатием: `GZipMiddleware` в коде приложения нет —
  поиск по `gzip` (без учёта регистра) во всех `.py` репозитория даёт четыре
  совпадения, и все четыре — в докстрингах и комментариях
  (`api/кэш_ассетов.py:23`, `api/meta_counts.py:8`,
  `scripts/посчитать_маршруты.py:35`, `tests/test_meta_counts.py:6`),
  ни одного — в коде middleware.

Расхождение объясняется в уже написанном (но ещё не закоммиченном) модуле
`api/кэш_ассетов.py:14-19`: «на проде к этому добавлялся `Cache-Control:
no-store`, который вставал на ответы без собственного заголовка кэша». То есть
поведение «no-store на всём» относится к **боевому** `helixcom.org`, который
замерять было запрещено. На песочнице `web-production-57f02` прокси так не
делает. Ниже все расчёты ведутся от замеренного, а не от предполагаемого.

### 2д. Условные запросы: 304 ОТВЕЧАЕТ (и это тоже против ожидания)

Ожидание из задания: «при no-store не должен». Поскольку на ассетах `no-store`
нет, 304 должен работать — и он работает.

|---|---|---|---|

`ETag` и `Last-Modified` на ассетах есть, 304 работает. Заголовка кэша на
ассетах нет — это и есть настоящая дефектная точка, а не `no-store`.

## ПУНКТ 4. Повторный визит: сколько байт качает второй заход

Считается арифметикой из пунктов 1–3, браузер не запускался.

### 4а. Исходные данные для расчёта

| Ресурс | Заголовок кэша на объекте | Поведение браузера |
|---|---|---|
| `/` (`index.html`) | `no-store, no-cache, must-revalidate, max-age=0` | всегда полная закачка, 1005 Б gzip; условный запрос не помог (200, см. 2д) |
| JS, CSS | заголовка нет; есть `ETag` + `Last-Modified` | эвристическая свежесть (RFC 9111 §4.2.2), после её истечения — условный запрос и 304 |
| `/openapi.json` | заголовка нет | но фронтенд зовёт его с `cache: 'no-store'` → HTTP-кэш обходится, всегда полная закачка |

Эвристическое окно для ассетов. Браузер при отсутствии `Cache-Control` и
`Expires`, но при наличии `Last-Modified`, обычно считает срок свежести как
10% от возраста файла:

```
Date:          Wed, 28 Oct 2026 01:06:07 GMT
Last-Modified: Tue, 27 Oct 2026 21:15:32 GMT
Возраст = 3 ч 50 мин 35 с = 13835 с
Эвристика = 13835 * 0.10 = 1383 с = 23 мин 3 с
```

**Окно ≈ 23 минуты** (и оно растёт вместе с возрастом файла: через сутки после
деплоя эвристика даст уже ~2.4 часа). Внутри окна повторный визит ассеты не
запрашивает вообще; после — шлёт два условных запроса и получает два 304.

### 4г. Что из этого следует

1. **Второй заход НЕ качает бандл заново** — вопреки исходному ожиданию в задании.
   На песочнице ассеты либо берутся из кэша молча, либо дают 304 с нулевым телом.
   Экономия на бандле: 205909 Б (JS+CSS gzip) = **81.4% от первого визита**.
2. **Но `openapi.json` качается ПОЛНОСТЬЮ на каждом показе титула**, включая
   повторные. Причина — не серверные заголовки (их на `/openapi.json` нет),
   а `{ cache: 'no-store' }` в самом фронтенде
   (`frontend/src/components/LandingHero.jsx:116` и `:129`). На повторном визите
   это **46000 Б из 47005 Б = 97.9% всего трафика**.
3. **Цена отсутствия `Cache-Control` на ассетах — не байты, а миллисекунды.**
   Как только эвристическое окно (~23 мин) истекает, каждый визит платит два
   лишних круга: 0.319 + 0.299 = **0.618 с**. При `immutable` этих двух запросов
   нет вообще.
4. **Каждый деплой обнуляет кэш у всех посетителей.** Vite кладёт в имя хэш
   содержимого, новая сборка даёт новые имена — и 205915 Б (бандл в gzip)
   скачиваются заново у каждого, независимо от любых заголовков. Это уже не
   гипотеза: за время между сборкой на живом объекте и пересборкой в рабочем
   дереве имена сменились с `index-CpimUzZB.js`/`index-C8koaoKB.css` на
   `index-B6bPs41Y.js`/`index-B97AsZLa.css`, а объём без сжатия вырос с
   695584 Б до 751787 Б (+56203 Б, +8.1%). После следующего деплоя каждый
   посетитель скачает этот объём целиком, а закэшированный старый бандл просто
   перестанет запрашиваться. Правка 1 (`immutable`) эту стоимость не снимает —
   она снимает только лишние проверки `ETag` между деплоями.
